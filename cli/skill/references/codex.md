# Running Lumo in Codex

Codex (CLI and desktop app) is a supported agent. `lumo init` (no `--agent`, or `--agent codex`) writes the repo's `.codex/hooks.json` and `.codex/rules/lumo.rules` ([onboarding.md](onboarding.md)); the user must **trust** the hooks once (Codex CLI `/hooks`, or the app's Settings → Hooks) and restart Codex so the rules load.

- **Network.** Codex's default sandbox has no network. The Lumo rules let `lumo` commands run outside it so they can reach the Lumo API; commands with local or human-only effects (writing local files, removing worktrees, uploading a local file, recording a human ruling) still make Codex ask first — request Codex's approval **with escalated (outside-sandbox) permissions up front** (the user is asked once), or have the user run them. Approving the rule's prompt alone runs the command inside the sandbox, where it cannot reach Lumo; Codex then asks a second time to rerun it outside (seen with Codex 0.162). The rules match the words right after `lumo`, so run `lumo …` as its own command with flags after the subcommand: `lumo a && lumo b` is fine, but `lumo … | head`, `> file` or `lumo --no-hints task …` runs sandboxed and fails with `could not reach Lumo API … (fetch failed)`. On that failure inside the sandbox the CLI appends a `Hint:` with the fix (re-run `lumo init` and restart Codex — a project's rules load only in a trusted project — or approve the command in Codex) — relay it. Hooks run outside the sandbox either way.
- **Session id.** Codex sets `CODEX_THREAD_ID` in every shell; it wins over a `CLAUDE_CODE_SESSION_ID` inherited from a parent Claude Code session. The session is `CODEX_SESSION_ID`; inside a Codex subagent the CLI uses the child session `<CODEX_SESSION_ID>:<CODEX_THREAD_ID>`, so a subagent's `session attach` is deterministic.
- **Hook trust self-check.** Codex skips untrusted hooks with no error. When the server has no hook event for this Codex session, `session attach` and `session status` print `no hook events have reached Lumo from this Codex session …` — relay it: the user must run `lumo init` (or `lumo init --agent codex`) and trust the `lumo hook …` entries; until then nothing of the session is recorded. When some Lumo events have no trust entry in `~/.codex/config.toml` (typically events added by re-running `lumo init`), both print `these Lumo hook events may not be trusted in Codex: <events>` — relay it: trust those entries in `/hooks`. The check is a text scan (hash not verified), hence "may". `lumo doctor` shows the same.
- **Session-start context** (the `[Lumo] session_id=…` line, the pointer to `lumo skill read`, the task context) arrives as developer context. If `hook: SessionStart Failed` shows and no `[Lumo] session_id=` line is in context, the CLI is too old: have the user run `lumo update`; `lumo session status` still works.
- **Events.** Codex has no PostToolUseFailure (a failed command is a normal PostToolUse), PermissionDenied, PostToolBatch, Worktree\*, FileChanged, ConfigChange, Notification or InstructionsLoaded — those signals are absent for Codex sessions.
- **Tools.** Codex writes files only through `apply_patch`, which counts as a write tool (collision warnings, sensitive-path and secret checks, deleted-test detection); reads go through `Bash`.
- **Token usage** comes from the Codex rollout files on every Stop (subagents from their own rollouts); an interrupted turn's usage lands with the next Stop. `lumo usage resync` is not needed for Codex.
- **Memory.** `memory sync` / `memory push` refuse in a Codex shell (they target Claude Code's memory store, which Codex never reads; `--dir` still writes explicitly). Team memory reaches Codex through `lumo task show --full` and the session-start hook.
