# Dashboard & Project Summary Redesign

**Date:** 2026-04-11
**Status:** Draft
**Scope:** Workspace Dashboard page, Project Detail → Summary tab, LLM summary generation pipeline, workspace/project risk threshold configuration.

---

## 1. Problem & Goals

### 1.1 Current State

The existing Dashboard (`components/pages/DashboardPage.tsx`) and Project Summary tab (`components/summary/ProjectSummaryTab.tsx`) both display essentially the same layout generated by the daily cron job (`/api/summaries/generate`):

1. `SummaryReportCard` — LLM-generated TL;DR and full markdown report (3 sections: Progress Overview / Risks & Blockers / Suggested Actions).
2. `StatsCardRow` — 4 headline numbers (total / completed / overdue / avg completion time).
3. `projectBreakdown` list (Dashboard only) — flat progress bars per project.
4. Three charts — status distribution, member workload, completion trend.
5. `AdditionalStats` — folded drawer with priority distribution, subtask rate, agent stats, PR stats.
6. `SummaryHistory` — on-demand history list.

### 1.2 Problems

- **No sense of priority.** A manager opening the Dashboard in the morning cannot tell in 3 seconds what is on fire. The TL;DR is there, but the layout buries urgent signal under neutral numbers and charts.
- **No project health concept.** "Progress" is shown as a flat percentage; there is no notion of "this project needs attention today."
- **LLM doubles as rules engine.** The LLM decides what counts as "risk" purely from prose instructions. This is non-deterministic — a project can be flagged today and ignored tomorrow with unchanged data.
- **Dashboard and Project Summary are near-duplicates.** The ProjectSummaryTab is literally a subset of the Dashboard with `projectBreakdown` removed. There is no distinct reason to visit it.
- **`AdditionalStats` is a junk drawer.** Four unrelated metrics collapsed into one panel, low information value.

### 1.3 Goals

1. **Dashboard serves the "manager's morning standup" use case.** First screen = "what should I act on today" + "which projects need attention". Numbers and charts are supporting material, not the lead.
2. **Introduce a deterministic project health model.** Hard rules assess each project as `healthy / watch / at-risk`. The LLM only narrates the rule output.
3. **Make risk thresholds configurable at workspace level, with per-project overrides.** Teams differ; a 5-person startup and a 50-person org should not share the same "overdue ratio ≥ 25%" cutoff.
4. **Unify Dashboard and Project Summary around the same mental model** — "drill down into a risky project". The Project tab reuses Dashboard's briefing card shape but narrows scope.
5. **Keep existing visualizations (charts, stat cards, history).** They remain valuable as secondary context.

### 1.4 Non-Goals

- Scheduled email briefings / PDF export.
- Customizing what the LLM writes about (only structure is prescribed).
- Re-computing historical summaries (backward compatibility is via runtime fallback, not backfill).
- Changing Prisma tables for `ProjectSummary` / `WorkspaceSummary`. Only `Workspace` and `Project` gain new columns.

### 2.2 Data Flow

```
Daily cron: GET /api/summaries/generate
  │
  ├─ summaryService.findSummaryEnabledWorkspaces()
  │    (Prisma query extended to include workspace risk fields + project risk fields)
  │
  ├─ for each workspace:
  │    ├─ for each project:
  │    │    effectiveConfig = resolveEffectiveRiskConfig(workspace, project)
  │    │    stats = aggregateProjectStats(project.id, effectiveConfig)
  │    │       └─ internal: computeRisk(stats, signals, config) → stats.risk
  │    │       └─ internal: collectTopBlockers(...) → stats.topBlockers
  │    │    report = generateProjectReport(stats, ctx)
  │    │    projectSummary = summaryService.createProjectSummary(...)
  │    │
  │    ├─ workspaceCfg = RiskConfig from workspace columns only
  │    ├─ projectRisks = Map<projectId, RiskAssessment>  // from step above
  │    ├─ workspaceStats = aggregateWorkspaceStats(workspace.id, workspaceCfg, projectRisks)
  │    │    └─ projectBreakdown[i].risk = projectRisks.get(i.projectId)  // not recomputed
  │    ├─ report = generateWorkspaceReport(workspaceStats, ctx)
  │    └─ workspaceSummary = summaryService.createWorkspaceSummary(...)
  │
  └─ return results
```

**Key invariants:**

- `computeRisk` is a pure function. No I/O, no time.now(). All temporal signals (`stalledTaskCount`, `last7dCompleted`, etc.) are computed by the caller and passed in as `signals`.
- `RiskConfig` is injected only from the cron route. Service and repository layers do not know about it — they stay focused on CRUD.
- Workspace `risk.level` is **the max of its projects' levels** (any project `at-risk` → workspace `at-risk`), not a re-aggregation from global stats. This prevents dilution hiding a single exploding project.

## 3. Risk Scoring Model

### 3.1 Type Definitions

In `types/summary.ts`:

```ts
export type RiskLevel = 'healthy' | 'watch' | 'at-risk'

export type RiskReasonCode =
  | 'overdue_ratio_high'
  | 'stalled_tasks'
  | 'agent_failure_rate'
  | 'stale_open_prs'
  | 'throughput_drop'

export interface RiskReason {
  code: RiskReasonCode
  detail: string // human-readable, e.g. "7/20 tasks overdue (35%)"

  score: number

  overdueTaskIds: string[] // max 10

  failingAgentTaskIds: string[] // consecutive failed ≥ 2, max 10

}

export interface TaskSummaryStats {
  // ...existing fields unchanged...
  risk: RiskAssessment
  topBlockers: TopBlockers // project-level only; empty arrays at workspace level
}

export interface WorkspaceSummaryStats extends TaskSummaryStats {
  projectBreakdown: Array<{
    projectId: string
    projectName: string
    totalTasks: number
    completedTasks: number
    overdueTasks: number
    risk: RiskAssessment // new
  }>

```

### 3.2 RiskConfig and Defaults

In `lib/summaries/risk.ts` (new file):

```ts
export interface RiskConfig {
  overdueRatio: number // 0–1, ratio threshold
  stalledDays: number // days without status change to count as stalled
  stalledMinCount: number // minimum stalled count to trigger rule
  agentFailRatio: number // 0–1
  stalePrDays: number // days PR open without review
  throughputDrop: number // 0–1, ratio of last7 to prev7
}

export const DEFAULT_RISK_CONFIG: RiskConfig = {
  overdueRatio: 0.25,
  stalledDays: 7,
  stalledMinCount: 3,
  agentFailRatio: 0.3,
  stalePrDays: 3,
  throughputDrop: 0.5,
}

const RISK_WEIGHTS: Record<RiskReasonCode, number> = {
  overdue_ratio_high: 3,
  stalled_tasks: 2,
  agent_failure_rate: 2,
  stale_open_prs: 1,
  throughput_drop: 2,
}

const RISK_BANDS = { HEALTHY_MAX: 2, WATCH_MAX: 4 } as const
// score 0–2 → healthy; 3–4 → watch; ≥ 5 → at-risk
```

Band thresholds are **not** user-configurable (keeps the settings UI tractable). Rule thresholds are per-workspace, per-project configurable.

### 3.3 Rule Definitions

| Code                 | Trigger                                                                                                                                             | Detail Template                                  |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| `overdue_ratio_high` | `overdueTasks.count / max(1, totalTasks) ≥ config.overdueRatio`                                                                                     | `"{overdue}/{total} tasks overdue ({pct}%)"`     |
| `stalled_tasks`      | `signals.stalledTaskCount ≥ config.stalledMinCount` (stalled = no status change in past `config.stalledDays` days AND status not in DONE/CANCELLED) | `"{N} tasks with no progress in {days} days"`    |
| `agent_failure_rate` | `agentStats.total ≥ 3 && agentStats.failed / agentStats.total ≥ config.agentFailRatio`                                                              | `"Agent failure rate {pct}% ({failed}/{total})"` |
| `stale_open_prs`     | `signals.staleOpenPrCount ≥ 1` (open > `config.stalePrDays` days AND no review; if review count unavailable, degrade to age-only)                   | `"{N} PRs waiting > {days} days for review"`     |
| `throughput_drop`    | `prev7dCompleted > 0 && last7dCompleted ≤ prev7dCompleted * config.throughputDrop`                                                                  | `"Completion dropped {pct}% week-over-week"`     |

**`stale_open_prs` degradation:** If the PR repository/query does not yet expose review counts, the first implementation pass uses age-only (any open PR older than `config.stalePrDays` days counts). This is explicitly accepted; the rule code and detail format stay the same so upgrading to review-aware later is transparent.

```ts
export function resolveEffectiveRiskConfig(
  workspace: Pick<

    | 'riskStalledDays'

    | 'riskAgentFailRatio'
    | 'riskStalePrDays'
    | 'riskThroughputDrop'
  >,

```

`resolveEffectiveRiskConfig` returns a `RiskConfig` where every field is `project?.riskXxx ?? workspace.riskXxx`. All workspace fields are guaranteed non-null (Prisma defaults); all project fields are nullable and `null` means "inherit."

### 3.5 Workspace-Level Aggregation

The logic below is internal to `aggregateWorkspaceStats` — it does **not** introduce a new exported function. It composes `computeRisk` (applied to workspace-aggregate stats) with a max-of-projects pass.

```ts
// Pseudocode — inlined inside aggregateWorkspaceStats
function internalWorkspaceRisk(
  workspaceStats: TaskSummaryStats,
  signals: Signals,
  config: RiskConfig,
  projectRisks: Map<string, RiskAssessment>
): RiskAssessment {
  // 1. Compute rule-based risk for the aggregate (same computeRisk function)
  const aggregateRisk = computeRisk(workspaceStats, signals, config)

  // 2. Compute max-of-projects risk
  const levels = [...projectRisks.values()].map(r => r.level)
  const maxLevel: RiskLevel = levels.includes('at-risk')
    ? 'at-risk'
    : levels.includes('watch')
      ? 'watch'
      : 'healthy'

  // 3. Workspace level is the worse of the two
  const finalLevel: RiskLevel = worseOf(aggregateRisk.level, maxLevel)

  // 4. Reasons: merge aggregate reasons + top-3 at-risk project names
  return {
    level: finalLevel,
    score: aggregateRisk.score,
    reasons: [
      ...aggregateRisk.reasons,
      ...topAtRiskProjectReasons(projectRisks /* max 3 */),
    ],
  }
}
```

## 4. LLM Prompt & Markdown Contract

### 4.1 Key Decision

**The LLM no longer decides risk.** The rules engine does. The LLM receives the pre-computed `RiskAssessment` in its prompt and writes two things:

1. `tldr`: A single headline sentence.
2. `report`: A markdown document with **exactly two sections**, fixed order and fixed headers.

### 4.2 Markdown Contract

```markdown
## Today's Focus

- <imperative action bullet>
- <imperative action bullet>
- <imperative action bullet>

## Risk

<1–2 sentences naming the level in plain language and citing at least one specific number from reasons[]>
```

For Chinese locale, section headers are `## 今日关注` and `## 风险`.

**Rules enforced via prompt:**

- Today's Focus: 2–4 bullets, each starts with an imperative verb, ≤ 15 words (en) / ≤ 20 characters (zh), ordered by priority (first bullet is most urgent).
- Risk: 1–2 sentences, must reference at least one number from the triggered `reasons[]`.
- If the project is healthy (no triggered rules), Today's Focus is lighter ("Keep momentum on X") and Risk says "No blockers detected."

### 4.3 System Prompt (English)

```
You are a project management analyst writing a briefing for an engineering lead's
daily standup.

A rules engine has already assessed the project's risk level. Your job is NOT to
re-assess risk — use the pre-computed level and triggered rules as ground truth.

Produce:
- tldr: One sentence (≤ 25 words) capturing the single most important thing the
  lead needs to know today.
- report: A Markdown document with EXACTLY these two sections, in this order:

## Today's Focus
2–4 bullet points. Each bullet must:
- Start with an imperative verb (Unblock, Review, Reassign, Fix, Ship…)
- Be ≤ 15 words
- Reference a specific person, task, or number from the stats when possible
- Be immediately actionable this week
- Be ordered by priority (first bullet is most urgent)

## Risk
1–2 sentences. State the risk level in plain language and explain it by citing
at least ONE specific number from the triggered rules. Do not list all rules —
synthesize.

Rules:
- Be factual. Every number you cite must come from the stats or the triggered rules.
- No preamble, no headings other than the two above, no emoji.
- If the project is healthy with no triggered rules, Today's Focus can be lighter
  ("Keep momentum on X") and Risk says "No blockers detected."
```

The Chinese version is structurally identical, with Chinese headers and verbs (`解除阻塞 / 审核 / 重新分配 / 修复 / 交付`).

```ts
function formatReasonsForPrompt(reasons: RiskReason[], locale: string): string {
  if (reasons.length === 0) {
    return locale.startsWith('zh') ? '(无触发规则)' : '(no triggered rules)'
  }
  return reasons.map(r => `  - [${r.code}] ${r.detail}`).join('\n')
}
```

### 4.6 Parsing — `lib/summaries/parse-report.ts`

```ts
export interface ParsedReport {
  todayFocus: string[] // bullet texts without the "- " prefix
  riskNarrative: string // plain paragraph text
  raw: string // original markdown
}

export function parseReport(report: string, locale: string): ParsedReport
```

**Algorithm:**

1. Build locale-specific header lookup: `{ focus: ['## Today\'s Focus', '## 今日关注'], risk: ['## Risk', '## 风险'] }`.
2. Split report by `/^## /m`. For each chunk, match header against lookup.
3. `todayFocus` = chunk body split on `/^[-*]\s+/m`, trimmed.
4. `riskNarrative` = chunk body, trimmed.
5. Always include `raw` = original report string.

**Degradation:** If neither header matches, return `{ todayFocus: [], riskNarrative: '', raw: report }`. UI uses `raw` as fallback.

### 4.7 Post-Generation Validation

`generateProjectReport` and `generateWorkspaceReport` call `parseReport` on the LLM output before returning. If **both** sections are empty (parsing totally failed), log a warning and proceed — the UI fallback handles it. **No retry in v1.** If the failure rate proves high later, add a one-shot retry with stricter instructions.

### 4.8 Backward Compatibility

| Scenario                                            | Behavior                                                                                                       |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Old `ProjectSummary.report` without section headers | `parseReport` returns empty sections; `BriefingCard` renders `raw` as a single text block                      |
| Old `ProjectSummary.stats` without `risk` field     | UI reads `stats.risk ?? undefined`; `RiskBadge` renders `null` state ("Not assessed"); no risk narrative shown |
| Next cron run                                       | New data format replaces old naturally; no backfill needed                                                     |

### 5.5 `ProjectsAtGlanceList`

Replaces the inline project-breakdown block in the current `DashboardPage`.

```ts
interface ProjectsAtGlanceListProps {
  projects: WorkspaceSummaryStats['projectBreakdown']
  onNavigate: (projectId: string) => void
}
```

**State:** `filter: 'all' | 'at-risk' | 'watch' | 'healthy'`, default `'all'`.

**Computed:**

```ts
const counts = useMemo(
  () => ({
    'at-risk': projects.filter(p => p.risk?.level === 'at-risk').length,
    watch: projects.filter(p => p.risk?.level === 'watch').length,
    healthy: projects.filter(p => p.risk?.level === 'healthy').length,
  }),
  [projects]
)

const order = { 'at-risk': 0, watch: 1, healthy: 2, null: 3 }
const sorted = useMemo(
  () =>
    [...projects].sort((a, b) => {
      const d = order[a.risk?.level ?? 'null'] - order[b.risk?.level ?? 'null']
      return d !== 0 ? d : b.overdueTasks - a.overdueTasks
    }),
  [projects]
)

const visible =
  filter === 'all' ? sorted : sorted.filter(p => p.risk?.level === filter)
```

**Row layout:**

```
● Project α                                    62%       7/20
  3 overdue, agent failing (40%)                        overdue
```

- Leading dot = `RiskBadge` size sm
- Progress bar + percentage
- Right column: `{completed}/{total}` and `{overdue} overdue` if > 0

### 5.9 Project Detail — Risk Thresholds Override Card

Added to the **Overview tab sidebar** in `ProjectDetailPage.tsx` (not the Summary tab — this is configuration, not observation). Positioned below the existing properties (Lead, etc.).

Default (collapsed) state:

```
┌─ Risk thresholds ──────────────────┐
│ Using workspace defaults           │
│ [Override defaults]                │
└─────────────────────────────────────┘
```

Expanded state:

```
┌─ Risk thresholds ──────────────────┐
│ Overdue ratio      [      ]  ⓘ     │  ← empty = inherit (shows workspace value as placeholder)
│ Stalled days       [  5  ] × ⓘ     │  ← has value = override, × button clears to inherit
│ Stalled min count  [      ]  ⓘ     │
│ Agent failure …    [      ]  ⓘ     │
│ Stale PR days      [      ]  ⓘ     │
│ Throughput drop    [      ]  ⓘ     │
│                                     │
│ [Reset all to workspace]  [Save]   │
└─────────────────────────────────────┘
```

Form state tracks each field as `{ value: number | '', dirty: boolean }`. Initial state mirrors DB: if the column is a number, `value = number, dirty = false`; if null, `value = '', dirty = false`. Any user interaction flips `dirty = true`.

On Save, build the payload by iterating only `dirty` fields:

- Dirty + `value === ''` → payload field is `null` (clear override, return to inheritance).
- Dirty + `value` is a number → payload field is the number (set override).
- Not dirty → field is omitted from payload entirely.

`PATCH /api/projects/[id]` only receives changed fields. Reset-all marks all 6 fields dirty with empty value → payload has all 6 as `null`.

## 7. Migration & Rollout

### 7.1 Deployment Order

1. Deploy Prisma migrations (both `add_workspace_risk_thresholds` and `add_project_risk_overrides`). All existing workspaces get defaults; all existing projects keep nulls.
2. Deploy backend code (risk engine, aggregation changes, prompt rewrite, API validation).
3. Next scheduled cron run produces new-format summaries.
4. Deploy frontend (new components, settings UIs).

Steps 2 and 4 can go in the same PR if convenient; step 1 must land first or at worst simultaneously with step 2.

### 7.2 Between Migration and First Cron Run

Old `ProjectSummary` rows are untouched — their `stats` JSON does not have `risk`, their `report` is in the old 3-section format. The new UI handles both:

- `BriefingCard` parses the old report → fallback to raw markdown display
- `RiskBadge` with `risk={undefined}` → "Not assessed"
- `ProjectsAtGlanceList` sorts unassessed projects last

After one cron cycle (typically 24 hours or as configured per workspace), all workspaces and projects have new-format data.

### 7.3 No Backfill

We accept that old summary history entries (shown in `SummaryHistory`) will display in old-format rendering. They are historical snapshots; rewriting them is unnecessary and would lose fidelity.

## 8. Open Questions (Deferred)

These are intentionally punted from v1:

1. **Per-project risk threshold presets.** Hand-typing 6 numbers per project is clunky. A future iteration could offer presets ("Strict / Standard / Lenient").
2. **Retry on parse failure.** If we observe the LLM frequently producing malformed markdown, add a one-shot retry with stricter prompting.
3. **PR review count.** Whenever the PR repository exposes review counts, upgrade `stale_open_prs` from age-only to age+no-review.
4. **Risk history / trend.** Showing "was watch yesterday, now at-risk" would require persisting `risk` on every summary and diffing. Worth doing after the base feature ships.
5. **Alert / notification on level change.** Out of scope; could be added via the existing notifications system.
