# Confirmation protocol (`--confirm`, exit code 4)

Some `lumo` commands change or destroy state that a human should sign off on first — deleting a sprint, milestone, document, memory, artifact or dependency edge; closing a sprint with unfinished tasks; removing or pruning worktrees, or running a repo's `verifyCommand`; re-deriving a doc's markdown source; moving a task to **DONE** (unless its one-step condition holds — a status-only update, every linked PR merged and nothing blocks, LUM-1106 / LUM-1116; see [tasks.md](tasks.md)). Since LUM-755 they all speak one protocol instead of prompting or hard-refusing:

1. You run the command **without `--confirm`**.
2. The CLI computes, from real server/local state, what it would do — and **does not do it**. It prints a **confirmation envelope on stdout** and exits **4**.
3. You show the envelope's `changes` to the user, verbatim.
4. The user approves or rejects.
5. Only on approval, you re-run the envelope's `confirmCommand` — the same invocation with `--confirm` appended.

There is no interactive yes/no prompt on a TTY either: a human and an agent walk the same steps.

## The envelope

When stdout is not a TTY (the agent path) the envelope is JSON:

```json
{
  "status": "confirmation_required",
  "command": "sprint delete",
  "changes": [
    "Will delete sprint #3 \"Sprint 3\"",
    "12 tasks under it keep their data; only sprintId is cleared"
  ],
  "confirmCommand": "lumo sprint delete 3 --confirm"
}
```

| Field            | Meaning                                                                                                                                                                                                         |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`         | Always `confirmation_required`.                                                                                                                                                                                 |
| `command`        | The command path, e.g. `task update`, `worktree rm`.                                                                                                                                                            |
| `changes`        | Human-readable lines describing exactly what would happen, computed from the current state (titles, counts, linked PRs, dirty files…). Never empty.                                                             |
| `confirmCommand` | Your original argv (flags and quoting preserved) plus `--confirm` — and, when a second gate applies, that gate's flag too (`--force --confirm`).                                                                |
| `statusSummary`  | Optional (LUM-842, `task update --status done` only): the task's current status digest — same read as `lumo task status`. Informational, not part of what the user approves; no follow-up `task status` needed. |

On a TTY the same fields are rendered as text: a header line, one `-` bullet per change, then `Re-run with --confirm once the user has approved:` and the command on its own line.

Nothing goes to stderr; the envelope is the command's result, not an error. **Exit 4 is the only signal you need** — do not grep the text to decide whether a command "wants confirmation".

## Rules for an agent

- **Exit 4 → stop and relay.** Print every line of `changes` to the user. Do not paraphrase away a `⚠` line.
- **Wait for an explicit approval.** A user who asked you to "delete the sprint" earlier has not yet seen what the envelope says will happen; the envelope is what they approve.
- **Run `confirmCommand` unchanged.** Do not rebuild the command by hand, do not drop flags the envelope carried (`--force`, `--team`, `--project`…).
- **Never add `--confirm` (or `--yes`, or `--force`) on your own initiative.** `--confirm` means "the user has confirmed". Passing it without that approval is the one thing this protocol exists to prevent, and it is visible in the session trail.
- A rejected envelope is not an error to retry — report the user's decision and move on.

## Flags

- `--confirm` — the user approved. Present on every command in the table below.
- `--yes` — legacy alias of `--confirm`, carried by the commands that took it before LUM-755 Prefer `--confirm` in new invocations. `task update` never had `--yes` and does not gain it.
- `--force` — a **second gate** that stays separate from `--confirm`: `worktree rm` uses it to acknowledge discarding uncommitted changes; `doc rebuild-source` uses it to acknowledge replacing an existing source. Missing `--force` also yields an envelope (exit 4) whose `confirmCommand` carries `--force --confirm`.
- `--confirm-read` + `--receipt <token>` — the **read-acknowledgement handshake** (LUM-769) on `crossing disposition`, a three-step protocol the _server_ enforces, the way a web form is loaded, "I have read this" is ticked, and only then submit works. **Step 1** (no step flag) reads the crossing and obtains a stage-1 receipt bound to the crossing, the ruling, your session/member and the crossing's current state (ruling, recurrence, explanations); its envelope's `confirmCommand` carries `--receipt <r1> --confirm-read`. **Step 2** (`--confirm-read`, after the user says they have read it) has the server verify r1 and return the stage-2 receipt; the CLI prints a second envelope for the ruling whose `confirmCommand` carries `--receipt <r2> --confirm`. **Step 3** (`--confirm`, after the user approves the ruling) writes. Confirming the ruling with the stage-1 receipt is refused — locally before any request, and by the server with 409 — and told to confirm the read first; a receipt that is missing, forged, expired (10-minute TTL), for another reader/ruling, or older than the crossing's latest change (a recurrence, a new explanation, a ruling) is refused too, nothing written — re-run without a step flag for a fresh envelope. Each envelope lists its receipt under `receipt: { token, expiresAt }`. The audit row records shown / read-acknowledged / confirmed times. This makes the order un-skippable; it does not, and cannot, prove the user personally ticked the box — you relay each step — so the ruling is recorded as a CLI-channel disposition. **Batch (LUM-845):** with several ids the same three steps run once for the whole batch — one envelope per step listing every crossing in full, one receipt per crossing carried as `--receipt <ref>=<token>,<ref>=<token>…`; dropping an id from the `confirmCommand` leaves that crossing OPEN (its receipt is ignored). See [verify.md](verify.md).

## When the gate is human-only: `DONE_BLOCKED`, exit code 5

Not every refusal is something the user can approve on the spot. The server's DONE gates — an **undispositioned boundary crossing**, a **blocking security finding**, a **proven test-case defect** — are verdicts on the agent's own work, and the interested party may not adjudicate itself: nothing on `task update` clears them — no `--confirm`, no `--force`, nothing you can pass. Since LUM-769 a **boundary crossing** does have a terminal path, but it is a separate command and it is the user's: `lumo crossing disposition <id> --false-positive | --confirmed` walks the exit-4 protocol above (you relay the crossing, the user rules, you re-run the `confirmCommand`). Security findings still have no CLI path at all (a proven test-case defect is ruled by the user through `lumo task testcase disposition`, see [test-cases.md](test-cases.md)).

What the CLI does instead: when `task update <id> --status done --confirm` is refused by one of these gates, it re-reads the task's status and open crossings, prints a structured error on **stdout** and exits **5** (it also carries the `statusSummary` digest described above, so no follow-up `task status` is needed):

```json
{
  "status": "blocked",
  "code": "DONE_BLOCKED",
  "command": "task update",
  "task": "LUM-48",
  "message": "Cannot move this task to DONE — 1 undispositioned boundary-crossing (forbidden action taken during this task): 1 TEST_FILE_DELETED. …",
  "blockers": [
    {
      "kind": "BOUNDARY_CROSSING",
      "id": "cmtw…",
      "ref": "LUM-X12",
      "severity": "MEDIUM",
      "category": "TEST_FILE_DELETED",
      "detail": "deleted __tests__/cli/old.test.ts"
    }
  ],
  "unconfirmed": [],
  "remediation": [
    "BOUNDARY_CROSSING: leave a rationale with `lumo crossing explain LUM-X12 --task LUM-48 --note \"…\"` (append-only; it does not clear anything), then relay each crossing to the user. Once they rule, record it with `lumo crossing disposition LUM-X12 --false-positive` or `--confirmed` — it prints an exit-4 envelope for the user to approve; never self-approve. The web panel also works: https://…/my-tasks/LUM-48#boundary-crossings"
  ],
  "dispositionUrl": "https://…/my-tasks/LUM-48#boundary-crossings"
}
```

| Field         | Meaning                                                                                                                                                                                                                                                                                                                                                                                                     |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `message`     | The server's 409 text, verbatim.                                                                                                                                                                                                                                                                                                                                                                            |
| `blockers`    | One entry per item holding the gate: `BOUNDARY_CROSSING` (id, severity, category, detail), `SECURITY_FINDING` (findingId, severity, ruleId, filePath, line, prNumber, statement). Built from the same read models as `lumo task status`. A `BOUNDARY_CROSSING` entry appears only for crossings the server gate counts (LUM-771): advisory crossings never, and with the workspace gate off only HIGH ones. |
| `nonBlocking` | Open crossings the gate does NOT count (id, severity, category, detail, advisory) — awareness only; do not ask the user to disposition them to get past DONE_BLOCKED. Rendered as a separate `Also open, not blocking DONE` list in the terminal (LUM-771).                                                                                                                                                 |
| `unconfirmed` | Enrichment reads that failed (`boundary-crossings read failed: HTTP 500`). Non-empty means the blocker list may be incomplete — it never silently shrinks.                                                                                                                                                                                                                                                  |
| `remediation` | One line per blocker kind present, naming only human-side, append-only or user-approved paths: `lumo crossing explain`, `lumo crossing disposition` / `lumo finding disposition` (exit-4 envelopes, the user rules), fix-and-push, the web disposition panel. Never a ready-to-run approval flag.                                                                                                           |

**Exit 4 vs exit 5:** 4 means "the user must approve, then you can proceed"; 5 means "a human must adjudicate — nothing on this command moves it". On exit 5, relay `blockers` and `remediation` to the user. Do not retry `task update`, and do not look for a flag on it. For a `BOUNDARY_CROSSING` or `SECURITY_FINDING` blocker the adjudication can happen in the terminal — `lumo crossing disposition <id> …` / `lumo finding disposition <findingId> …` are themselves exit-4 commands, so the user's ruling still comes through the protocol, never from you. Once every blocker is cleared, re-run the original `task update … --confirm` (its envelope was already approved). A 409 that is not a DONE gate (e.g. a permission refusal) keeps the plain exit-1 text on stderr.

## Example exchange

(With every linked PR merged and nothing blocking, the same command would run in one step instead — LUM-1106. Here #930 is open, so it stops.)

```bash
lumo task update LUM-48 --status done
# exit 4, stdout:
# {
#   "status": "confirmation_required",
#   "command": "task update",
#   "changes": [
#     "Will move LUM-48 \"Panel refactor\" to DONE",
#     "Status: IN_REVIEW → DONE",
#     "#926  merged   refactor: panel  https://github.com/o/r/pull/926",
#     "#930  open     feat: wip        https://github.com/o/r/pull/930",
#     "⚠ 1 linked pull request not merged: #930 open"
#   ],
#   "confirmCommand": "lumo task update LUM-48 --status done --confirm"
# }
```

Agent → user: "Moving LUM-48 to DONE would change IN_REVIEW → DONE. PR #926 is merged, but **#930 is still open**. Confirm?" — and only after a yes:

```bash
lumo task update LUM-48 --status done --confirm
```
